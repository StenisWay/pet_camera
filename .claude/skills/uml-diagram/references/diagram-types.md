# 各圖型的擺放規則與語意約定

每一節的順序：**這張圖回答什麼問題 → 元素上限 → 擺放規則 → 常見畫錯**。
選圖型時先看「回答什麼問題」，不要照使用者說的名字直接畫——他說「畫個架構圖」時，
要的可能是元件圖、部署圖，或其實是循序圖。

---

## 類別圖 Class Diagram

**回答**：系統裡有哪些概念、彼此怎麼關聯、誰繼承誰。
**上限**：12–15 個類別。超過就依 bounded context 拆。

**擺放**
- 繼承／實作：父在上、子在下，永遠不要倒過來。
- 組合／聚合：整體在上、部分在下（`Order *-- OrderLine`）。
- 關聯／依賴：水平擺，跟垂直的階層線區隔開。
- 介面放在實作它的類別**上方**，用 `.up.>` 連。

**關係符號別用錯**（這是唯一比版面更容易被行家抓包的地方）

| 語意 | 符號 | 判準 |
|---|---|---|
| 繼承 | `A <|-- B` | B is-a A |
| 實作 | `A <|.. B` | B 實作介面 A |
| 組合 | `A *-- B` | A 死了 B 跟著死（訂單與訂單明細） |
| 聚合 | `A o-- B` | A 死了 B 還在（車隊與車） |
| 關聯 | `A -- B` | 單純知道彼此 |
| 依賴 | `A ..> B` | 只在參數／回傳值出現，不持有 |

多重性寫在線的兩端，用 `1`、`0..1`、`1..*`、`0..*`。**每條關聯都要標**，沒標等於沒說清楚。

**常見畫錯**：把資料表當類別畫（那是 ER 圖）；把每個 getter/setter 都列出來（只列有意義的行為）；
用繼承表達「有一個」關係。

## 循序圖 Sequence Diagram

**回答**：這件事發生時，誰先呼叫誰、順序為何、哪裡會失敗。
**上限**：5–7 條生命線。超過就把某幾個參與者收成一個「子系統」。

**擺放**
- 生命線由左至右：**使用者 → 介面 → 控制／服務 → 資料層 → 外部系統**。
  呼叫大多往右流，回頭線最少，這是循序圖最重要的一條規則。
- 回傳值用虛線 `-->`，只畫**有意義**的回傳（拿到 token、拿到清單），
  每個呼叫都畫回傳會讓圖多一倍高度卻沒多資訊。
- 錯誤路徑用 `alt/else`，非同步用 `->>`（不等回應）。

**版面**
```
skinparam maxMessageSize 110    ' 循序圖最有效的一行，先加這個
skinparam ParticipantPadding 8
autonumber                       ' 訊息編號，讓文件可以引用「第 4 步」
```
`maxMessageSize` 實測讓一張 5 生命線的圖從長寬比 2.64 降到 1.14。

**常見畫錯**：把 if/else 畫成兩條分開的訊息（要用 `alt`）；
把非同步事件畫成同步呼叫（推播、webhook 要用 `->>` 並標明不等回應）。

## 狀態圖 State Diagram

**回答**：這個東西有哪些狀態、什麼事件讓它換狀態。
**上限**：8–12 個狀態。

**擺放**
- 初始狀態 `[*]` 在**左上**，終止狀態在**右下**，時間感由左上往右下。
- 主要成功路徑排成一條直線，例外狀態往側邊掛。
- 每條轉換都要標**事件**（可加 `[守衛條件] / 動作`），沒標事件的箭頭等於沒說為什麼會換狀態。

**判準**：狀態是「物件在某段時間的狀況」（`待付款`、`已出貨`），不是動作（`付款`）。
節點名寫成動詞就是畫錯了，那是活動圖。

## 活動圖／流程圖 Activity Diagram

**回答**：這個流程怎麼走、哪裡分岔、哪裡會失敗。
**上限**：主幹 15–20 步。

**擺放**
- 主幹垂直往下，**固定同一個 x**，讀者一眼看得到主線。
- 判斷節點的「否／失敗」分支一律往**同一側**（建議右），成功繼續往下。
- 迴圈（重試）往**左側**回收，跟右邊的錯誤分支分開，兩邊不打架。
- 平行流程用 `fork/join`，不要用兩條各走各的線假裝平行。

**太長怎麼辦**：折成兩欄蛇形——第一欄往下走到一半，跨到第二欄繼續往下。
這是把細長流程圖拉回 0.75–1.35 最有效的一招（見 `layout-toolbox.md` 的座標版做法）。

## 使用案例圖 Use Case Diagram

**回答**：誰能用這個系統做什麼。給非技術讀者看的。
**上限**：10–12 個 use case。

**擺放**
- 主要 actor 在**左**，系統邊界 `rectangle` 在中間，外部系統 actor 在**右**。
- `<<include>>` 指向被包含者，`<<extend>>` 指向被擴充者——方向常被畫反，
  記法：include 是「我一定會用到它」，箭頭從主流程指出去。
- use case 用**動詞片語**命名（`重設密碼`），不是名詞（`密碼管理`）。

**常見畫錯**：把系統內部步驟當 use case（那是活動圖）；
每個 CRUD 都畫一個框（合併成「管理裝置」）。

## 元件圖 / 部署圖 Component & Deployment

這兩張常被混為一談，**分清楚它們回答的問題**：

| | 元件圖 | 部署圖 |
|---|---|---|
| 回答 | 軟體怎麼切、誰依賴誰 | 東西跑在哪台機器上 |
| 節點 | 元件、介面 | node（VM／容器）＋ artifact |
| 邊 | 依賴、提供／需要介面 | 網路連線（標協定） |

**擺放**：分層排列，上層依賴下層（client → API → 資料層 → 外部服務），
同一層水平並排。部署邊界用框，**框要先宣告**（否則蓋住內容）。

**交叉線爆炸時**：多半是同一層有 N 個複本各連 M 個下游（N×M 條線）。
兩個解法——(1) 走共用匯流排（見 `layout-toolbox.md` 的 corridor/bus），
(2) 拆成「部署圖（誰在哪台機器）」＋「元件互動圖（誰呼叫誰，不畫機器邊界）」兩張。
硬塞成一張的結果就是誰也讀不懂。

## ER 圖 Entity Relationship

**回答**：資料表長怎樣、外鍵怎麼連。

**線要接在欄位上，不是接在表格上。** 這是 schema 圖與「概念關聯圖」的分界：
一條從 `users` 方框拉到 `devices` 方框的線只說得出「這兩張表有關係」；
一條從 `users.id` 那一列拉到 `devices.user_id` 那一列的線，說得出**是哪個欄位參照哪個欄位**。
讀者要據此寫 migration 或 join，後者才夠用。工具上這代表表格必須是「容器 + 每欄一個子格」
的結構（draw.io 的 swimlane + 子格、PlantUML 的 `entity` + 欄位錨點），而不是一整塊文字。

**擺放**
- 被最多表參照的表放**中央或上方**（通常是 `users`），線往四方散出去。
- 一對多：`1` 端在上或在左，`N` 端在下或在右，方向語意跟組合關係一致。
- 分兩欄擺時，把**被參照的一方全部放同一欄**，外鍵線就會一律同向（例如一律由左往右），
  讀者不必逐條追方向。
- 每條線標上**基數**（`1—N`），nullable 的外鍵要標出來（`1—N (NULL 允許)`）——
  `0..1` 跟 `1` 的差別就是實作時的 NOT NULL。
- 欄位列表左對齊、等寬字，`PK`／`FK` 標記對齊成一欄，讀者掃一眼就找得到鍵。

**常見漏掉**：資料模型文件裡有、圖上卻沒有的表。畫完拿文件的資料表清單逐一核對，
別只畫「有關係的那幾張」——沒被畫進去的表，讀者會以為它不存在。

**常見畫錯**：把多對多畫成一條線（要畫出中間的關聯表）；
nullable 的外鍵沒標（`0..1` 跟 `1` 的差別是實作時的 NOT NULL）。

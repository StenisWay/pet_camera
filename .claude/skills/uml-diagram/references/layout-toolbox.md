## PlantUML 版面參數

### 間距
```
skinparam nodesep 40      ' 同一層元素的左右間距（預設較大）
skinparam ranksep 45      ' 層與層的上下間距
skinparam padding 2
skinparam ParticipantPadding 8   ' 循序圖生命線間距
skinparam BoxPadding 10
```
**縮間距只縮面積，不救比例。** 實測 `nodesep 40 / ranksep 45` 讓面積少 20%，
長寬比反而從 1.53 變 1.68。要救比例得靠重排，不是靠壓縮。

### 方框體積
```
hide empty members                  ' 沒欄位的類別不留空格子
skinparam classAttributeIconSize 0  ' 拿掉 +/- 圖示，方框窄一截
skinparam shadowing false
skinparam roundcorner 4
```

### 線的走法
```
skinparam linetype ortho      ' 直角線：多線平行時好讀
skinparam linetype polyline   ' 折線：介於直線與直角之間
```
`ortho` **不改變尺寸**，只改變線怎麼繞。搭配 `nodesep` < 40 會讓多重性標籤壓在方框上，
要用就把 `nodesep` 開大。

## 方向控制

### 全域方向
```
left to right direction
```
只在圖**原本就太高**時用。對已經偏寬的圖用它會壓成細長條（實測 1.53 → 2.65）。
改完必須重新渲染確認，這是最容易弄巧成拙的一招。

### 單條邊的方向
```
A -down-> B     ' 也可寫 -->（預設 down）
A -up-> B
A -left-> B
A -right-> B
A -[hidden]down- B    ' 隱形線：只影響擺放，不畫出來
```

**箭頭方向是排版指令，不只是畫線指令。** PlantUML 依方向決定層次，
所以 `-left->` 會把 B 排到 A 左邊，即使語意上 A 依賴 B。

### 隱形線的三種用法

```
' 1. 把並排的兄弟疊成上下（拉正比例最有效）
CreditCardPayment -[hidden]down- BankTransferPayment

' 2. 強制兩個沒有關係的元素相鄰（讓相關的東西擺在一起）
Logger -[hidden]right- Metrics

' 3. 撐開距離（連續多條把元素推遠）
A -[hidden]down- spacer1
spacer1 -[hidden]down- B
```

`together { A B C }` 實測幾乎無效（1.51 vs 1.50），**別依賴它**；
真的要控制相鄰就用隱形線。

## 收斂的量測流程

```bash
python3 scripts/check_layout.py diagram.puml     # 需要 plantuml 或 PLANTUML_JAR
python3 scripts/check_layout.py diagram.drawio   # 直接算座標，不需渲染器
```

腳本回報：尺寸、長寬比、節點數 vs 上限、方向統計、交叉線、線壓到方框，
並把「太寬／太高」換算成具體動作（往幾欄收、折幾欄）。

**每改一次就重量一次。** 版面改動的效果無法用想的——第一次折疊把比例從 1.53
弄壞成 2.18 是真實發生過的事。

## draw.io（座標版）的等價手法

在 draw.io 裡座標是自己指定的，比 PlantUML 更可控，三原則照樣適用：

| 原則 | PlantUML | draw.io |
|---|---|---|
| 主幹垂直 | `-down->` | 主幹所有節點共用同一個 `x` |
| 分支往側邊 | `-right->` | 錯誤節點 `x = 主幹x + 280`，`y` 對齊來源 |
| 拉正比例 | `-[hidden]down-` | **兩欄蛇形**：主幹走到一半跨到右欄繼續 |
| 減少交叉 | 調宣告順序 | 線道（lane）：一條線一條路，並依來源高低排序 |

### 兩欄蛇形的座標

```
COL_GAP = 600           # 欄距 = 主幹寬 + 錯誤欄寬 + 淨空
ROW_PITCH = 120         # 每列高度（節點 60–80 + 箭頭空間）

第 1 欄主幹 x = X0            錯誤節點 x = X0 + 280
第 2 欄主幹 x = X0 + COL_GAP  錯誤節點 x = X0 + COL_GAP + 280
```

**跨欄那條線**是蛇形唯一的難點：它從第 1 欄底部回到第 2 欄頂部，視覺上往上走。
走法：從來源右側出去 → 沿一條淨空的垂直走廊往上 → 從左側進入第 2 欄第一個節點。
走廊 x 要挑在「第 1 欄錯誤欄的右邊、第 2 欄主幹的左邊」，也就是 `X0 + COL_GAP - 60`。

折幾欄不要用猜的：**把 1、2、3 欄各算一次 bbox，挑長寬比最接近 1.0 的**。
折疊會讓寬度乘 k、高度除 k，長寬比大約乘 k²——0.44 的圖折 2 欄會變 1.76（過頭），
這時要同時調 `ROW_PITCH` 或每欄列數才落得進 0.75–1.35。

### 錨點：線接在哪一點

| 邊 | exitX/exitY（entryX/entryY 同值） | 矩形上是 | 菱形上是 |
|---|---|---|---|
| 上 | `0.5, 0` | 上緣中點 | 上頂點 |
| 右 | `1, 0.5` | 右緣中點 | 右頂點 |
| 下 | `0.5, 1` | 下緣中點 | 下頂點 |
| 左 | `0, 0.5` | 左緣中點 | 左頂點 |

菱形內接於自己的方框，所以同一組比例值在兩種形狀上都落在對的位置，不必分開處理。

寫進 edge 的 style：

```
edgeStyle=orthogonalEdgeStyle;rounded=0;html=1;jettySize=auto;
exitX=0.5;exitY=1;exitDx=0;exitDy=0;entryX=0.5;entryY=0;entryDx=0;entryDy=0;
```

**`exitDx`/`exitDy` 要一起寫 0**，只寫 X/Y 的話 draw.io 有些版本會忽略整組設定。

哪一邊出、哪一邊進，由幾何決定，不要憑感覺挑：
第一個繞線點決定從哪邊離開來源，最後一個決定從哪邊進入目標；沒有繞線點時比較兩個
中心，用 `|dx|·h` 與 `|dy|·w` 相比（拿方框自身的長寬當權重），大的那個軸勝出。

**錨點與相鄰繞線點必須共線。** 上下錨點要共用 x、左右錨點要共用 y；不共線的話工具會
在形狀旁邊補一段小折線，那就是「線沒接好、有間隙」的樣子。修法是把繞線點推到錨點的
軸上（`drawio_gen.align_waypoints()` 做的就是這件事），而不是去改錨點。

**同一側多條線 → 錨點要沿邊分開。** 上面的中點值是「只有一條線」時的預設。
同一個節點同一側接了 k 條線時，改用 `1/(k+1)`、`2/(k+1)`…把它們沿那條邊排開：

| 幾條線 | exitY（左右側）或 exitX（上下側） |
|---|---|
| 1 | `0.5` |
| 2 | `0.33` `0.67` |
| 3 | `0.25` `0.5` `0.75` |
| 4 | `0.2` `0.4` `0.6` `0.8` |

理由是重疊：共用一個錨點的線會從同一點以同一個方向出發，在分岔之前完全重合，
看起來只有一條。schema 圖裡 `users.id` 連到三張表就是典型情況——三條線要看得出是三條。
排的順序依「對面那一端的位置」，線才不會在節點旁邊自己先交叉。
出線與進線一起算：一個節點左側有 1 條進線 + 3 條出線，就是 4 條一起分。

**只有矩形類可以這樣分散**（方框、資料表、欄位列、容器）。菱形與橢圓不行：

| 形狀 | 邊上真正碰得到形狀的點 |
|---|---|
| 矩形 | 整條邊 → 可沿邊分散 |
| 菱形 | 只有四個頂點 → 一個頂點一條線 |
| 橢圓 | 只有四個中點 → 一個點一條線 |

菱形的 `(0.33, 0)` 落在外接方框的上緣，但那裡是空白，形狀在更下面——箭頭會停在
半空中，看起來完全沒接到東西。判斷節點的同一個頂點要接第二條線時，唯一的解法是
**改接別的頂點**（迴圈通常繞到還沒被用掉的那一側），不是把錨點推開。

菱形一共只有四個接點。「上進、下出、左右分支」用滿之後就沒有位置了：
一個四向分支的判斷節點（進線 1 + 出線 4）必然有兩條線共用同一個頂點，
這時把共用的那一段壓到最短（出頂點後立刻轉向），並在交付說明裡標成已知例外。

### 線道（lanes）：一條線一條路，不共用

同一層多個來源要連到下方多個目標時（N×M 條線），**每條線各走一條專屬的垂直線道
與專屬的水平帶**，不要讓它們疊在同一條線上。

```
1. 每個來源從側邊出去，走自己的垂直線道（彼此相隔 20–30px）
2. 沿自己的水平帶走到目標的 x（帶與帶之間同樣相隔 20–25px）
3. 垂直進入目標
```

**不要做共用匯流排。** 把多條線疊成一條「匯流排」看起來很整齊，但讀者無法分辨那裡
到底有幾條線、哪條通到哪；交叉只是一個點，仍看得出是兩條線各走各的，重疊卻是一整段，
兩條線直接變成同一條。**重疊比交叉嚴重**——要在兩者之間取捨時，寧可多一個交叉點。

唯一容許的重疊，是**共用端點的線在那個端點旁邊的短樁**：從同一個錨點出發的線本來就
得先重合一小段才分得開，但要盡早分岔，不要並行整段路。

### 線道的排序決定會不會交叉

線道有幾條不重要，**排列順序**才決定交叉數。兩條規則一起用，整組線就是單調的：

1. **來源越低的邊，線道排越內側**（越靠近來源那一欄）。
   上方來源的水平出線段只會經過比自己更內側的線道，而那些線道的垂直段都在更下方，
   兩者碰不到。反過來排，條條相交。
2. **線道越內側，配到的水平帶越上面**。垂直段因此越短，不會切到別人的帶。

實測：一張 19 條線的架構圖，線道亂配是 31 處重疊；改成一線一道、再套上這兩條排序規則，
重疊降到 0、交叉從 31 降到 15。

一個容易踩的坑：**來源夾在障礙物與線道之間時**，它往線道的那一段會切過障礙物。
檢查每個來源實際落在障礙物的哪一側，別假設一條線道夠用。

### 有些交叉是結構性的，消不掉

例如 schema 圖裡同一欄的兩條外鍵（`users.id → devices.user_id` 與
`devices.id → events.device_id`）：PK 列永遠在 FK 列上方，所以兩條線的縱向區間必然
重疊 30px 左右，不管線道怎麼排都會交叉一次。這種要在交付說明裡講清楚為什麼消不掉，
而不是繼續調參數。

### 進入容器（container）的邊

容器是虛線空框，只有頂部約 26px 是標題帶。從**頂部**進入容器內的元件會壓到標題文字，
改從**側邊**水平進入（走廊沿目標的中心 y 過去），就不會壓到。

## Mermaid 對照

Mermaid 幾乎沒有版面手把，只有這些：

```mermaid
flowchart TD        %% TD 上下 / LR 左右 —— 幾乎是唯一的版面控制
  A --> B
  A ~~~ C           %% 隱形線（新版才有）
  subgraph 分組
    B --> C
  end
```

- `classDiagram`／`sequenceDiagram`／`stateDiagram-v2`／`erDiagram` 都不吃方向細調。
- 節點宣告順序會影響排列，這是 Mermaid 唯一可靠的排版手法。
- **在意版面就別用 Mermaid。** 它的優勢只有「GitHub/Notion 貼上就能看」。

## 1. 設計原則

- Postgres 只放 metadata,不放二進位大檔案。
- 影片、縮圖一律存 R2,DB 只存 object key。
- R2 的保留期完全交給 lifecycle rule 處理。

## 2. Postgres 資料表

九張表共用同一個資料庫(不做 database-per-service,見 `13_ADR_微服務與三節點部署.md` 第 5 節),
表的擁有權見該 ADR 第 1 節。可執行版本(SQLAlchemy model 與 Alembic migration)在 `db/`。

### 2.0 共同欄位與慣例

- 每張表都有 `id`、`created_at`、`updated_at`。`updated_at` 由 trigger `set_updated_at()` 維護,
  不依賴應用程式寫入——七個服務寫同一個庫,漏寫只是時間問題。
- 時間一律 `timestamptz`,以 UTC 儲存,顯示時才轉時區。
- `id` 為 uuid。資料庫預設值是 `gen_random_uuid()`(直接用 psql 塞測試資料時的保險),
  應用程式建立資料時應產生 **UUIDv7**:id 會出現在 R2 object key 與 API 路徑上,
  需分散產生,而 UUIDv7 有時間排序、對 B-tree 索引友善。
- 狀態欄位用 `text` + `CHECK` 約束表達值域,不用 PG enum(日後新增狀態值只要改 CHECK)。
- 外鍵的 `ON DELETE` 行為逐欄標註於下方各表,設計理由見第 6 節。

### 2.1 `users`

| 欄位 | 型別 | 說明 |
|---|---|---|
| id | uuid, PK | |
| email | text, unique | 登入帳號;一律以小寫儲存(`CHECK email = lower(email)`),否則 `A@x.com` 與 `a@x.com` 會成為兩個帳號 |
| password_hash | text, nullable | bcrypt/argon2 雜湊;僅透過第三方登入建立且尚未設定過密碼的帳號為 `null`,見 `02_spec_登入註冊與密碼重設.md` 第 2.7 節 |
| failed_login_attempts | int, not null, default 0 | 連續帳密登入失敗次數,成功登入或鎖定期滿後歸零(見 `02_spec_登入註冊與密碼重設.md` 第 2.3 節) |
| locked_until | timestamptz, nullable | 鎖定到期時間;`null` 或已過期即未鎖定 |
| created_at | timestamptz | |
| updated_at | timestamptz | |

登入失敗計數存在 Postgres 而非 Redis,是因為 Redis 不做持久化(第 7.2 節):若計數放 Redis,重啟 Redis 就等於清空所有帳號的鎖定,暴力破解防護會有一個可被主動觸發的旁路。這也與 `13_ADR_微服務與三節點部署.md` 第 4 節「Auth 一律選一致性(C)」一致。

### 2.2 `devices`

| 欄位 | 型別 | 說明 |
|---|---|---|
| id | uuid, PK | |
| user_id | uuid, FK -> users.id, nullable, ON DELETE SET NULL | 未配對(`pending`)時為 `null`;解除配對與刪除帳號都會清空回 `null`,裝置可重新配對給別人(見第 6 節) |
| name | text | 使用者自訂鏡頭名稱 |
| pairing_code | text, nullable | 配對階段使用,配對完成後失效(清為 `null`);有效期間內不可重複,以部分唯一索引(`where pairing_code is not null`)強制 |
| pairing_code_expires_at | timestamptz, nullable | 與 `pairing_code` 同時存在或同時為 `null` |
| status | text | `pending` / `paired` / `offline`;`status = 'pending'` 與 `user_id is null` 必須同時成立(`offline` 是已配對裝置失聯,仍有擁有者) |
| last_seen_at | timestamptz, nullable | 心跳時間 |
| created_at | timestamptz | |
| updated_at | timestamptz | |

索引:`(user_id)`,部分唯一索引:`(pairing_code) where pairing_code is not null`。

### 2.3 `events`

| event_type | text | 目前僅 `motion` |
| confidence_score | numeric(3,2) | 0.00~1.00,以 CHECK 強制 |
| status | text | `processing` / `ready` / `failed`,見第 4 節 |
| video_object_key | text, nullable | 對應 R2 物件 key;`processing` 期間尚未上傳完成,故可為 `null`,`status = 'ready'` 時必填 |
| thumbnail_object_key | text, nullable | 同上 |
| duration_sec | int, nullable | 實際錄影長度;`ready` 時必填,值須 > 0 |
| started_at | timestamptz | 事件開始時間 |
| ended_at | timestamptz, nullable | `ready` 時必填,且不早於 `started_at` |
| is_read | boolean, default false | |
| is_partial | boolean, default false | 錄影因鏡頭斷線提前結束:片段可播放但不完整,時間軸據此顯示 `EVENT_003`(見 `07_spec_事件偵測與自動錄影.md` 第 3、5 節)。與 `failed` 是兩回事——`failed` 是沒有可播放內容 |
| created_at | timestamptz | |
| updated_at | timestamptz | |

索引:`(device_id, started_at desc)`。

對外 API 的時間欄位一律以 **Unix timestamp**(秒)呈現,見 `08_spec_時間軸與事件歷史.md`
第 2.1 節;儲存層維持第 2.0 節的 `timestamptz`,轉換由各服務的 presentation 層負責。

### 2.4 `media_items`

使用者從攝影機畫面主動截圖或剪輯保存的照片/短片,存放於相簿,獨立於 `events` 的自動保留機制(見第 3.2、6 節)。

| 欄位 | 型別 | 說明 |
|---|---|---|
| id | uuid, PK | |
| user_id | uuid, FK -> users.id, ON DELETE CASCADE | 刪除帳號時一併刪除(見第 6 節) |
| device_id | uuid, FK -> devices.id, ON DELETE RESTRICT | 裝置紀錄不會被刪除(解除配對只重置為 `pending`);用 RESTRICT 讓誤刪 `devices` 列直接失敗,而不是安靜帶走相簿資料 |
| source_event_id | uuid, FK -> events.id, nullable, ON DELETE SET NULL | 若從既有事件剪輯而來則填入,截圖亦可能來自即時畫面(此時為 null)。來源事件被刪除時只清空此欄,相簿項目本身保留 |
| type | text | `photo` / `clip` |
| object_key | text, nullable | 對應 R2 物件 key;`processing` 期間尚未產生,`status = 'ready'` 時必填 |
| thumbnail_object_key | text, nullable | `clip` 類型才有;`photo` 必為 `null` |
| duration_sec | int, nullable | `clip` 類型才有;`photo` 必為 `null`,值須 > 0 |
| status | text | `processing` / `ready` / `failed` |
| captured_at | timestamptz | 用於相簿依日期分組 |
| drive_export_status | text, default `not_exported` | `not_exported` / `exporting` / `exported` / `failed` |
| drive_file_id | text, nullable | 匯出成功後的 Google Drive 檔案 id;與 `drive_export_status = 'exported'` 同時成立 |
| created_at | timestamptz | |
| updated_at | timestamptz | |

索引:`(user_id, captured_at desc, id)`、`(device_id)`、`(source_event_id)`。

第一個索引把 `id` 一併納入,是因為相簿分頁用的是 `(captured_at, id)` 組合游標(見 `12_spec_相簿與雲端匯出.md` 第 2.1 節)——同一秒保存的多個項目若只靠 `captured_at` 分頁,使用者往下捲時會重複或漏掉項目。

`drive_export_status`、`drive_file_id` 兩欄由 **Album 服務**寫入,其餘欄位由 **Media 服務**寫入(見 `13_ADR_微服務與三節點部署.md` 第 1 節)。匯出逾時判定(`exporting` 停留超過 15 分鐘改判 `failed`)直接用第 2.0 節的 `updated_at`,不另外增加欄位:處於 `exporting` 的項目不會再被 Media 服務寫入,`updated_at` 即為該次匯出的開始時間。

### 2.5 `refresh_tokens`

僅 Web 平台使用(見 `02_spec_登入註冊與密碼重設.md` 第 2.3.1 節),App 平台不寫入此表。

| 欄位 | 型別 | 說明 |
|---|---|---|
| id | uuid, PK | |
| user_id | uuid, FK -> users.id, ON DELETE CASCADE | |
| token_hash | text, unique | refresh token 雜湊值,不存明碼 |
| expires_at | timestamptz | 簽發時間 + 30 天 |
| revoked_at | timestamptz, nullable | 登出或 rotation 換發舊 token 時標記 |
| created_at | timestamptz | |
| updated_at | timestamptz | |

索引:`(user_id)`,部分索引:`(user_id) where revoked_at is null`(驗證時只查未撤銷的紀錄)。
每次 rotation 換發新 token 時,將舊紀錄的 `revoked_at` 標記為當下時間,並新增一筆新紀錄,不覆寫舊紀錄(保留換發軌跡供異常排查)。

### 2.6 `push_tokens`

App/Web 用戶端向後端登記的推播接收端點(見 `09_spec_推播通知.md` 第 2.4、3 節)。與 `devices`(攝影機硬體)是不同概念,不可混用。

| 欄位 | 型別 | 說明 |
|---|---|---|
| id | uuid, PK | |
| user_id | uuid, FK -> users.id, ON DELETE CASCADE | |
| platform | text | `app` / `web` |
| token | text | FCM/APNs registration token,或 Web Push subscription(JSON 字串) |
| created_at | timestamptz | |
| updated_at | timestamptz | |

索引:`(user_id)`,唯一索引:`(platform, md5(token))`——同一個端點重複登記會讓使用者同一則通知收兩遍;
用 `md5()` 是因為 Web Push subscription 為 JSON 字串,直接建 B-tree 索引有長度上限風險。

### 2.7 `oauth_identities`

第三方登入(Google/Apple)綁定紀錄,見 `02_spec_登入註冊與密碼重設.md` 第 2.7 節。一個 `users` 可對應多筆(例如同一使用者分別綁定 Google 與 Apple),同一 provider 帳號僅能綁定一個 `users`。

| 欄位 | 型別 | 說明 |
|---|---|---|
| id | uuid, PK | |
| user_id | uuid, FK -> users.id, ON DELETE CASCADE | |
| provider | text | `google` / `apple` |
| provider_user_id | text | 該 provider 回傳的使用者唯一識別碼(Google `sub` / Apple `sub`) |
| email | text, nullable | 登入當下 provider 回傳的 email 快照(Apple 私密轉寄信箱時為該轉寄地址);Apple 僅在首次授權回傳 email,之後的登入可能沒有,故可為 `null` |
| created_at | timestamptz | |
| updated_at | timestamptz | |

索引:`(user_id)`,唯一索引:`(provider, provider_user_id)`、`(user_id, provider)`。
後者避免同一使用者把兩個 Google 帳號綁到同一個 `users`,登入時無法判斷該用哪一筆。

### 2.8 `google_drive_credentials`

Google Drive 匯出的授權憑證,由 **Album 服務**擁有,見 `12_spec_相簿與雲端匯出.md` 第 2.3 節。

與 2.7 的 `oauth_identities` 是不同概念,不可混用:那是「用 Google/Apple 帳號登入本系統」的身分綁定;這是「把相簿內容上傳到使用者自己的 Google Drive」的 `drive.file` 授權,scope、生命週期與撤銷時機都不同(使用者可以只解除 Drive 授權而繼續用 Google 登入)。

| 欄位 | 型別 | 說明 |
|---|---|---|
| id | uuid, PK | |
| user_id | uuid, FK -> users.id, unique, ON DELETE CASCADE | 一個使用者最多一份 Drive 授權 |
| refresh_token | text | Google OAuth refresh token。**需加密存放**,加密方式待確認 |
| drive_folder_id | text, nullable | 使用者 Drive 內「寵物攝影機」資料夾的 id,首次匯出時建立並寫回 |
| connected_at | timestamptz | 最近一次完成授權的時間 |
| created_at | timestamptz | |
| updated_at | timestamptz | |

唯一索引:`(user_id)`。

授權失效時(`DRIVE_003`,Google 回 `invalid_grant`)由 Album 服務刪除該筆紀錄,使用者下次匯出會得到 `DRIVE_001` 並被導回授權頁。只申請 `drive.file` scope,因此系統只看得到本 App 建立的檔案,碰不到使用者既有的雲端硬碟內容。

### 2.9 `password_reset_tokens`

忘記密碼流程的一次性重設 token,由 **Auth 服務**擁有,見 `02_spec_登入註冊與密碼重設.md` 第 2.4 節。

| 欄位 | 型別 | 說明 |
|---|---|---|
| id | uuid, PK | |
| user_id | uuid, FK -> users.id, ON DELETE CASCADE | |
| token_hash | text, unique | 重設 token 的雜湊值,不存明碼(與 `refresh_tokens` 同樣的理由:DB 外洩不等於可重設任何人的密碼) |
| expires_at | timestamptz | 簽發時間 + 30 分鐘 |
| used_at | timestamptz, nullable | 使用後標記,不刪除紀錄(保留軌跡供異常排查);`used_at is not null` 即不可再用 |
| created_at | timestamptz | |
| updated_at | timestamptz | |

索引:`(user_id)`,部分索引:`(user_id) where used_at is null`。

不放共用 Redis 的理由同 2.1 節的登入失敗計數:Redis 不做持久化,重啟會讓所有已寄出的重設連結
同時失效,使用者看到的是「剛收到的信就說連結已失效」;而第 7 節已明定 Redis 用途固定三項,
密碼重設屬於需要可回溯的一次性憑證,不符合該節「遺失內容不影響正確性」的前提。

### 2.10 不存入 DB 的內容

影片檔案內容、縮圖 base64 一律不進資料庫,只存 R2 object key。

## 3. R2 物件儲存結構

### 3.1 Key 命名規則

```
videos/{device_id}/{yyyy}/{mm}/{dd}/{event_id}.mp4
thumbnails/{device_id}/{yyyy}/{mm}/{dd}/{event_id}.jpg
media/{user_id}/{yyyy}/{mm}/{dd}/{media_item_id}.{mp4|jpg}
media-thumbnails/{user_id}/{yyyy}/{mm}/{dd}/{media_item_id}.jpg
```

`media/`、`media-thumbnails/` 對應 `media_items`(使用者手動保存的截圖/剪輯),key 以 `user_id` 分層,與依 `device_id` 分層的事件影片區隔。

### 3.2 Lifecycle Rule

| Prefix | 保留天數 |
|---|---|
| `videos/` | 7 天 |
| `thumbnails/` | 30 天 |
| `media/`、`media-thumbnails/` | 不設 lifecycle rule,保留至使用者手動刪除 |

影片過期後 `events` 表紀錄仍保留,`video_object_key` 欄位不刪除。`media_items` 為使用者主動保存的內容,不受自動保留期限制,由使用者自行管理(見 `12_spec_相簿與雲端匯出.md`)。

### 3.3 存取方式

- 上傳:由 Backend API 或偵測 worker 直接寫入 R2。
- 下載/播放:App/Web 呼叫 Backend API 換取一次性 presigned URL(有效期 10 分鐘)。
- **例外**:推播通知夾帶的事件縮圖 URL 效期為 **30 分鐘**(見 `09_spec_推播通知.md`
  第 2.2 節)。10 分鐘是使用者點播時當下換發的效期;推播經 APNs/FCM 可能延遲或重送,
  沿用 10 分鐘會讓通知裡的圖在送達前就失效。

## 4. 事件處理狀態機

| 狀態 | 說明 |
|---|---|
| `processing` | 錄影中或上傳中,尚無可播放影片 |
| `ready` | 影片與縮圖已上傳完成,可查詢與播放 |
| `failed` | 上傳失敗,不建立可播放內容 |

時間軸(F3)依此狀態決定顯示方式,見 `08_spec_時間軸與事件歷史.md`。

## 5. 相簿項目狀態機

| 狀態 | 說明 |
|---|---|
| `processing` | 截圖處理中或剪輯轉檔中,尚無可用內容 |
| `ready` | 照片/剪輯已產生完成,可於相簿查詢與播放 |
| `failed` | 處理失敗,不建立可用內容 |

相簿(F6)依此狀態決定顯示方式,見 `12_spec_相簿與雲端匯出.md`。

## 6. 刪除與串聯清除規則

| 觸發動作 | 串聯行為 |
|---|---|
| 移除裝置(unpair) | 立即刪除該 `device_id` 底下所有 `events` 紀錄,以及對應的 R2 影片與縮圖物件(不等待 lifecycle rule 到期)——由 Device 服務呼叫 **Event 服務**的內部端點 `DELETE /internal/devices/{device_id}/events` 執行,R2 物件也由 Event 刪除,因為 key 需要 `event_id` 與事件日期,Device 組不出來(見 `08_spec_時間軸與事件歷史.md` 第 3.3 節);`devices` 紀錄狀態重置為 `pending`,`user_id` 清空,`pairing_code` 重新產生。該裝置來源的 `media_items` **不受影響**,使用者已保存至相簿的內容視為使用者資產,與來源裝置的生命週期脫鉤 |
| 刪除帳號 | 由 Auth 服務呼叫 Device 服務的內部端點 `DELETE /internal/users/{user_id}/devices`(見 `04_spec_裝置管理.md` 第 3 節)串聯執行上述「移除裝置」邏輯於該帳號名下所有裝置,刪除該帳號所有 `media_items` 與對應 R2 物件(由 Auth 服務呼叫 Album 服務的內部端點 `DELETE /internal/users/{user_id}/media`,見 `12_spec_相簿與雲端匯出.md` 第 3 節),刪除該帳號所有 `refresh_tokens`、`password_reset_tokens`、`push_tokens`、`oauth_identities`、`google_drive_credentials` 紀錄,再刪除 `users` 紀錄 |

**何時需要內部清除端點**:只有「刪掉資料列還不夠」的服務才需要——Device(連帶刪 R2 影片與縮圖)與 Album(連帶刪 R2 媒體物件)各提供一個,外鍵管不到物件儲存。其餘跨服務的表(`push_tokens`、`google_drive_credentials`)沒有外部副作用,一律由外鍵 `ON DELETE CASCADE` 隨 `users` 帶走,不另外開端點。這不違反 `13_ADR_微服務與三節點部署.md` 第 1 節的邊界原則:CASCADE 是資料庫在維護參照完整性,約束定義在共用的 `db/migrations/`,不是 Auth 服務去寫別人的表。

移除裝置時一併清除歷史事件,理由:裝置未來可能被重新配對給不同使用者,避免新使用者看到前一位使用者的寵物活動紀錄。

## 7. Redis 共用狀態

除第 2 節 Postgres 資料表外,系統另提供一個共用 Redis 單例,存放不需要持久化的短效共享狀態。Redis 的定位、單例部署方式與新增理由見 `13_ADR_微服務與三節點部署.md` 第 1.1 節。

### 7.1 用途與 Key 結構

| 用途 | Key 格式 | TTL | 對應規格書 |
|---|---|---|---|
| Stream 訊令 session 暫存 | `stream:session:{session_id}` | 隨 session 建立時設定,session 結束或逾時即清除(數分鐘量級) | `06_spec_即時串流.md` |
| Push 防洗版計數窗 | `push:window:{device_id}` | 5 分鐘 | `09_spec_推播通知.md` 第 2.3 節 |
| 全站請求限流 | `ratelimit:{user_id 或 ip}:{endpoint}` | 依限流窗口長度(如 1 分鐘) | `10_錯誤處理與狀態規範.md` |

### 7.2 設計原則

- Redis 不存放任何需要長期保留或可回溯稽核的資料;內容遺失最多造成使用者需重新建立一次連線、短暫多收一次推播、或短暫限流失準,不影響任何 Postgres 資料的正確性。
- 不做 Redis 複寫或 AOF/RDB 持久化——內容本質上是快取/暫存性質,重啟後清空可接受,理由見 `13_ADR_微服務與三節點部署.md` 第 4、5 節。
- 用途固定為以上三項,不作為 Postgres 查詢結果的通用快取層,擴大範圍的觸發條件見 `13_ADR_微服務與三節點部署.md` 第 5 節。

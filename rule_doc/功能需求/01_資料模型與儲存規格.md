## 1. 設計原則

- Postgres 只放 metadata,不放二進位大檔案。
- 影片、縮圖一律存 R2,DB 只存 object key。
- R2 的保留期完全交給 lifecycle rule 處理。

### 2.4 `media_items`

| 欄位 | 型別 | 說明 |
|---|---|---|
| id | uuid, PK | |
| user_id | uuid, FK -> users.id | |
| device_id | uuid, FK -> devices.id | |

| thumbnail_object_key | text, nullable | `clip` 類型才有 |
| duration_sec | int, nullable | `clip` 類型才有 |
| status | text | `processing` / `ready` / `failed` |
| captured_at | timestamptz | 用於相簿依日期分組 |
| drive_export_status | text | `not_exported` / `exporting` / `exported` / `failed` |

| created_at | timestamptz | |

### 2.5 `refresh_tokens`

僅 Web 平台使用(見 `02_spec_登入註冊與密碼重設.md` 第 2.3.1 節),App 平台不寫入此表。

| 欄位 | 型別 | 說明 |
|---|---|---|
| id | uuid, PK | |
| user_id | uuid, FK -> users.id | |
| token_hash | text | refresh token 雜湊值,不存明碼 |
| expires_at | timestamptz | 簽發時間 + 30 天 |
| revoked_at | timestamptz, nullable | 登出或 rotation 換發舊 token 時標記 |
| created_at | timestamptz | |

索引:`(user_id)`。每次 rotation 換發新 token 時,將舊紀錄的 `revoked_at` 標記為當下時間,並新增一筆新紀錄,不覆寫舊紀錄(保留換發軌跡供異常排查)。

### 2.6 `push_tokens`

App/Web 用戶端向後端登記的推播接收端點(見 `09_spec_推播通知.md` 第 2.4、3 節)。與 `devices`(攝影機硬體)是不同概念,不可混用。

| 欄位 | 型別 | 說明 |
|---|---|---|
| id | uuid, PK | |
| user_id | uuid, FK -> users.id | |
| platform | text | `app` / `web` |
| token | text | FCM/APNs registration token,或 Web Push subscription(JSON 字串) |
| created_at | timestamptz | |

索引:`(user_id)`。

### 2.7 `oauth_identities`

第三方登入(Google/Apple)綁定紀錄,見 `02_spec_登入註冊與密碼重設.md` 第 2.7 節。一個 `users` 可對應多筆(例如同一使用者分別綁定 Google 與 Apple),同一 provider 帳號僅能綁定一個 `users`。

| 欄位 | 型別 | 說明 |
|---|---|---|
| id | uuid, PK | |
| user_id | uuid, FK -> users.id | |
| provider | text | `google` / `apple` |
| provider_user_id | text | 該 provider 回傳的使用者唯一識別碼(Google `sub` / Apple `sub`) |
| email | text | 登入當下 provider 回傳的 email 快照(Apple 私密轉寄信箱時為該轉寄地址) |
| created_at | timestamptz | |

索引:`(user_id)`,唯一索引:`(provider, provider_user_id)`。

### 2.8 不存入 DB 的內容

影片檔案內容、縮圖 base64 一律不進資料庫,只存 R2 object key。

## 3. R2 物件儲存結構

### 3.1 Key 命名規則

```
videos/{device_id}/{yyyy}/{mm}/{dd}/{event_id}.mp4
thumbnails/{device_id}/{yyyy}/{mm}/{dd}/{event_id}.jpg
media/{user_id}/{yyyy}/{mm}/{dd}/{media_item_id}.{mp4|jpg}
media-thumbnails/{user_id}/{yyyy}/{mm}/{dd}/{media_item_id}.jpg
```

`media/`、`media-thumbnails/` 對應 `media_items`(使用者手動保存的截圖/剪輯),key 以 `user_id` 分層,與依 `device_id` 分層的事件影片區隔。

### 3.2 Lifecycle Rule

| Prefix | 保留天數 |
|---|---|
| `videos/` | 7 天 |
| `thumbnails/` | 30 天 |
| `media/`、`media-thumbnails/` | 不設 lifecycle rule,保留至使用者手動刪除 |

影片過期後 `events` 表紀錄仍保留,`video_object_key` 欄位不刪除。`media_items` 為使用者主動保存的內容,不受自動保留期限制,由使用者自行管理(見 `12_spec_相簿與雲端匯出.md`)。

### 3.3 存取方式

- 上傳:由 Backend API 或偵測 worker 直接寫入 R2。
- 下載/播放:App/Web 呼叫 Backend API 換取一次性 presigned URL(有效期 10 分鐘)。

## 4. 事件處理狀態機

| 狀態 | 說明 |
|---|---|
| `processing` | 錄影中或上傳中,尚無可播放影片 |
| `ready` | 影片與縮圖已上傳完成,可查詢與播放 |
| `failed` | 上傳失敗,不建立可播放內容 |

時間軸(F3)依此狀態決定顯示方式,見 `08_spec_時間軸與事件歷史.md`。

## 5. 相簿項目狀態機

| 狀態 | 說明 |
|---|---|
| `processing` | 截圖處理中或剪輯轉檔中,尚無可用內容 |
| `ready` | 照片/剪輯已產生完成,可於相簿查詢與播放 |
| `failed` | 處理失敗,不建立可用內容 |

相簿(F6)依此狀態決定顯示方式,見 `12_spec_相簿與雲端匯出.md`。

## 6. 刪除與串聯清除規則

| 觸發動作 | 串聯行為 |
|---|---|
| 移除裝置(unpair) | 立即刪除該 `device_id` 底下所有 `events` 紀錄,以及對應的 R2 影片與縮圖物件(不等待 lifecycle rule 到期);`devices` 紀錄狀態重置為 `pending`,`user_id` 清空,`pairing_code` 重新產生。該裝置來源的 `media_items` **不受影響**,使用者已保存至相簿的內容視為使用者資產,與來源裝置的生命週期脫鉤 |
| 刪除帳號 | 串聯執行上述「移除裝置」邏輯於該帳號名下所有裝置,刪除該帳號所有 `media_items` 與對應 R2 物件,刪除該帳號所有 `refresh_tokens`、`push_tokens` 紀錄,再刪除 `users` 紀錄 |

移除裝置時一併清除歷史事件,理由:裝置未來可能被重新配對給不同使用者,避免新使用者看到前一位使用者的寵物活動紀錄。

## 7. Redis 共用狀態

除第 2 節 Postgres 資料表外,系統另提供一個共用 Redis 單例,存放不需要持久化的短效共享狀態。Redis 的定位、單例部署方式與新增理由見 `13_ADR_微服務與三節點部署.md` 第 1.1 節。

### 7.1 用途與 Key 結構

| 用途 | Key 格式 | TTL | 對應規格書 |
|---|---|---|---|
| Stream 訊令 session 暫存 | `stream:session:{session_id}` | 隨 session 建立時設定,session 結束或逾時即清除(數分鐘量級) | `06_spec_即時串流.md` |
| Push 防洗版計數窗 | `push:window:{device_id}` | 5 分鐘 | `09_spec_推播通知.md` 第 2.3 節 |
| 全站請求限流 | `ratelimit:{user_id 或 ip}:{endpoint}` | 依限流窗口長度(如 1 分鐘) | `10_錯誤處理與狀態規範.md` |

### 7.2 設計原則

- Redis 不存放任何需要長期保留或可回溯稽核的資料;內容遺失最多造成使用者需重新建立一次連線、短暫多收一次推播、或短暫限流失準,不影響任何 Postgres 資料的正確性。
- 不做 Redis 複寫或 AOF/RDB 持久化——內容本質上是快取/暫存性質,重啟後清空可接受,理由見 `13_ADR_微服務與三節點部署.md` 第 4、5 節。
- 用途固定為以上三項,不作為 Postgres 查詢結果的通用快取層,擴大範圍的觸發條件見 `13_ADR_微服務與三節點部署.md` 第 5 節。

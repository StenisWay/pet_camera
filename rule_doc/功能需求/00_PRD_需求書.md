## 1. 產品背景

飼主外出時需要掌握寵物在家的狀況。系統提供即時畫面查看、自動事件錄影與通知,讓使用者不需持續盯著直播畫面也能掌握寵物動態。

## 2. 產品目標與目標使用者

**目標使用者**:家中有貓/狗、單一鏡頭、單一使用者的一般消費者。

**平台範圍**:手機一律使用原生 App(iOS/Android,需從 App Store / Google Play 下載安裝);Web 採 RWD,依視窗/螢幕尺寸自適應(桌機、筆電、平板皆可正常使用)。判斷是否導向 App 下載的依據是**作業系統**,不是螢幕寬度:User-Agent 偵測到 iOS 或 Android 手機時,一律導向對應商店的 App 下載頁,不渲染任何 Web 介面;非手機作業系統一律視為桌面瀏覽器,正常提供 RWD 後的 Web 體驗(見 `screens/web/02_page_導覽與全域結構.md` 第 0 節)。

**產品目標**:
- 使用者能隨時打開 App/Web 看到鏡頭即時畫面
- 鏡頭偵測到寵物活動時自動錄影並推播通知
- 使用者能回顧過去幾天的事件時間軸並觀看片段

## 4. 核心使用者故事

1. 作為飼主,我想要打開 App 立刻看到鏡頭現場畫面。
2. 作為飼主,我希望寵物在鏡頭前活動時系統自動錄下來。
3. 作為飼主,我想收到手機通知,知道剛剛家裡發生了什麼事。
4. 作為飼主,我想滑一下今天的時間軸,快速看過哪些時段寵物有動靜。
5. 作為飼主,我想第一次使用時能順利把鏡頭跟我的帳號配對起來。

## 5. 系統架構

後端拆分為微服務,部署在三台 Oracle Always Free Ampere A1 VM(VM-1、VM-2 各 1 OCPU / 6GB 跑無狀態服務複本,VM-3:2 OCPU / 12GB 集中所有單例元件,由 4 OCPU / 24GB 免費額度依負載型態切分),前面掛一個 Oracle Flexible Load Balancer。完整拓撲、元件與連線標註見 `diagrams/00_architecture_系統架構圖.drawio`;決策理由與取捨見 `13_ADR_微服務與三節點部署.md`。

**架構決策**:
- 功能拆成七個獨立服務(Auth / Device / Event / Stream 訊令 / Push / Media / Album),VM-1、VM-2 各跑一份複本,由 Load Balancer 分流,提供基本容錯與水平擴展能力;每台 VM 上的 Nginx 依路徑把請求分派到各服務,服務間呼叫亦經本機 Nginx,見 `14_API閘道與路由規範.md`;各服務與資料表的對應關係見 `13_ADR_微服務與三節點部署.md` 第 1 節。
- Postgres 為單例,不做複寫,固定跑在獨立的 VM-3;所有服務複本(VM-1、VM-2)皆透過 VCN 私有網路連線至 VM-3,不對外開放。
- Redis 為單例,與 Postgres 同置於 VM-3,提供 Stream 訊令 session、推播防洗版計數、全站限流等不需持久化的短效共享狀態,不做複寫,細節見 `13_ADR_微服務與三節點部署.md` 第 1.1 節。
- 事件偵測 worker 為單例,固定跑在 VM-3,並直接接收鏡頭裝置的 RTSP 串流(不經 Load Balancer);與 Postgres 同機,事件寫入不經過網路。
- TURN server 為單例,固定跑在 VM-3,App/Web 的 WebRTC media relay 直連(不經 Load Balancer)。
- 四個單例元件(Postgres、Redis、事件偵測 worker、TURN server)全部集中在 VM-3,VM-1、VM-2 維持純無狀態、完全對稱;VM-3 因此分到較多資源(2 OCPU / 12GB)。
- Web 前端的靜態檔(HTML/JS/CSS)由 **Cloudflare Pages** 託管,不由任何 VM 供應、也不經過 Load Balancer;瀏覽器先向 Pages 載入前端,之後的 API 呼叫才走 LB。頁面是瀏覽器端渲染,系統內沒有伺服器端渲染的角色。
- 影片與縮圖不進資料庫,一律存 R2,DB 只存 metadata 與 object key;R2 用 lifecycle rule 做保留期自動清理。
- 不做 database-per-service、不做 CQRS——現階段規模不需要,理由見 ADR。

## 6. 非功能需求(NFR)

| 類別 | 需求 |
|---|---|
| 直播延遲 | App 開啟直播頁到看到首幀畫面 < 3 秒 |
| 事件可見延遲 | 從偵測觸發到片段出現在時間軸 < 30 秒 |
| 資料保留 | 事件影片保留 7 天,縮圖保留 30 天;相簿(使用者手動保存的截圖/剪輯)不設自動保留期限 |
| 安全性 | 傳輸全程 TLS;密碼雜湊儲存(bcrypt/argon2);影片存取一律透過短效期(10 分鐘)presigned URL |
| 成本上限 | 落在 Oracle Always Free + Cloudflare R2／Pages 免費層額度內 |
| 可用性 | API 服務層雙節點 + Load Balancer,單一節點故障不中斷服務;Postgres、事件偵測 worker、TURN server 皆為單例,無高可用設計 |
| 錯誤處理 | 全站錯誤顯示與狀態規範見 `10_錯誤處理與狀態規範.md` |

## 8. 名詞定義

| 名詞 | 定義 |
|---|---|
| 事件(Event) | 系統偵測到寵物活動並產生一段錄影的紀錄,對應 `events` 資料表一筆 |
| 信心分數(Confidence Score) | 偵測服務對「這是一次有效活動」的信心值,0~1 |
| Presigned URL | R2 發出的短效期直接存取連結,繞過後端代理直接傳輸檔案 |
| TURN Server | WebRTC 連線失敗直連時的中繼伺服器,所有影音流量經過它轉發 |
| 保留期(Retention) | 影片/縮圖在 R2 上被 lifecycle rule 自動刪除前的存活天數 |
| 相簿項目(Media Item) | 使用者從攝影機畫面主動截圖或剪輯保存的照片/短片,對應 `media_items` 資料表一筆,不受自動保留期限制 |

## 9. 瓶頸分析

依「最先被撞到的上限」排序:

1. TURN 伺服器流量(免費額度約 1000GB/月量級)
2. VM-3 的 CPU(事件偵測與 ffmpeg 剪輯轉檔皆為運算密集,且固定在單一節點、不可分攤到 VM-1/VM-2)
3. R2 操作次數(上傳/下載次數)
4. R2 儲存容量(10GB 免費額度)

拆成三台 VM(1+1+2 OCPU)後,運算總量與原本一台 4 OCPU 相同,並未增加也未減少——真正改變的是可用性(API 層有備援)、可觀測性(每服務獨立監控),以及無狀態服務層與單例元件層的職責分離,詳見 `13_ADR_微服務與三節點部署.md`。

### 9.1 這些瓶頸的擴展路徑(都不是 Load Balancer)

**Load Balancer 只在 API 路徑上,跟上面前兩名瓶頸完全無關。** API 是唯一不吃力的路徑
(單一使用者、幾支鏡頭的 JSON 請求),LB 存在的理由是節點容錯,不是分擔負載
(見 `13_ADR_微服務與三節點部署.md` 第 3 節)。真正會撞上限的三件事各有各的解法:

| 瓶頸 | 擴展手段 | 為什麼不能用 LB |
|---|---|---|
| TURN 中繼流量 | ① **先讓流量不要經過 TURN**:P2P/STUN 直連成功時媒體不進伺服器(見 `06_spec_即時串流.md`),提高直連成功率是最大的一條槓桿,其次是降低解析度/位元率。② 真的需要多台時,由 **Stream 訊令服務在建立 session 時分配**要用哪一台 TURN。 | WebRTC 媒體是 UDP、有狀態、session 綁定同一台中繼,中途換機即斷線;分流必須發生在**分配時**,不是讓流量穿過 L7 LB。何況免費版 LB 只有 10 Mbps,把媒體導進去是最糟的位置。 |
| VM-3 的 CPU(事件偵測 + ffmpeg) | 依 `device_id` **分片**成多個 worker,各自負責一部分鏡頭 | worker 不接受外部請求,它主動拉 RTSP 串流,前面沒有可以分流的入口 |
| R2 操作次數/容量 | lifecycle rule 自動清理(已實施)、縮圖與影片分開設保留期 | 存取本來就由瀏覽器憑 presigned URL 直連 R2,不經過任何自有伺服器 |

**觸發點**:以上三項都維持現況,直到實測撞到免費額度或延遲有感為止。特別注意
TURN 那一列的順序——先確認 P2P 成功率是否偏低(通常是 NAT 類型或防火牆造成),
再考慮開第二台 TURN;順序反了會白花資源在中繼上。

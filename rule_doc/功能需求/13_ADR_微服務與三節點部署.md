## 1. 決策

後端由單體服務改為拆分成獨立容器,部署在三台 Oracle Always Free Ampere A1 VM,由 4 OCPU / 24GB 免費額度依負載型態切分為 VM-1(1 OCPU / 6GB)+ VM-2(1 OCPU / 6GB)+ VM-3(2 OCPU / 12GB),前面掛一個 Oracle Flexible Load Balancer。切分原則是**無狀態複本與單例元件分開**:VM-1、VM-2 只跑可被 LB 分流的服務複本、彼此完全對稱;所有不能分流的單例元件(Postgres、Redis、事件偵測 worker、TURN server)集中在 VM-3,因此 VM-3 分到較多資源。

拆分邊界對應功能規格書的 F-number,分成七個服務:

| 服務 | 涵蓋 F-number | 擁有的資料表 |
|---|---|---|
| Auth | F0.1(登入註冊密碼重設)+ F0.4(帳號設定) | `users`、`refresh_tokens` |
| Device | F0.2(裝置配對)+ F0.3(裝置管理) | `devices` |
| Event | F2(事件偵測,背景 worker,不對外提供 API)+ F3(時間軸讀取 API) | `events` |
| Stream 訊令 | F1 | 無(session 狀態存於共用 Redis,見第 1.1 節與 `interfaces/backend/stream/`) |
| Push | F4 | `push_tokens` |
| Media | F5 | `media_items`(擁有者,負責寫入) |
| Album | F6 | 讀取/管理 `media_items`(與 Media 共用同一張表,見下方說明) |

F0.4(帳號設定)併入 Auth 服務,而非獨立成一個服務——兩者都是對 `users` 表的操作(密碼雜湊驗證、帳號生命週期),拆開會變成兩個服務搶同一張表的寫入權,沒有實質邊界效益。

Event 服務同時涵蓋 F2 與 F3,是因為兩者都圍繞同一張 `events` 表:F2 的偵測 worker 負責寫入,F3 的時間軸 API 負責讀取,兩者拆開會變成兩個服務各自宣稱擁有同一張表,違反「一服務一資料表」的邊界原則。

Media 與 Album 共用 `media_items` 表(Media 寫入截圖/剪輯,Album 讀取/刪除/匯出),是本次拆分裡唯一沒有做到「一服務一資料表」的例外——因為兩者對應到兩份不同的功能規格書(F5、F6),硬併成一個服務會模糊「錄製來源」跟「使用者相簿管理」這兩個不同的使用情境。因此 Album 服務在程式介面上**不直接引用 Media 服務的型別定義**,而是自行定義一份對應同一張表的唯讀視圖(見 `interfaces/backend/album/`),兩服務各自可獨立部署替換,只是底層剛好指向同一張表。

### 1.1 共用 Redis:基礎設施層,不是第八個服務

除 Postgres 外,系統另提供一個共用 Redis 單例,存放不需要持久化、生命週期短的共享狀態,用途限定三項:

| 用途 | 使用服務 | 對應規格書 |
|---|---|---|
| Stream 訊令 session 暫存(TURN 憑證、SDP 交換過程) | Stream 訊令 | `06_spec_即時串流.md` |
| 推播防洗版計數窗 | Push | `09_spec_推播通知.md` 第 2.3 節 |
| 全站請求限流(`RATE_001`) | 所有服務共用 | `10_錯誤處理與狀態規範.md` |

新增 Redis 的直接原因是 Stream 訊令服務的一個實際問題:兩台 VM 各跑一份 Stream 服務複本,Load Balancer 以請求為單位分流,同一個 session 的「建立 session」「送出 offer」「結束 session」三個請求可能被分派到不同複本。若 session 狀態存在服務本機記憶體,跨複本的請求會讀不到對方寫入的狀態,連線建立會隨機失敗。Redis 提供兩台複本都能存取的共享暫存,解決這個問題,且天生支援 TTL,符合「session 狀態為短效」的需求。Push 的防洗版計數與全站限流則是相同性質的高頻、短效狀態,一併用同一個 Redis 承接,不另外各自开一套機制。

Redis 定位與 Postgres 相同:單例、不做複寫、固定跑在同一個節點(VM-3,見下方節點分工),透過 VCN 私有網路連線,不對外開放,細節見第 3、4 節。之所以不算違反「不做 database-per-service」的原則(第 5 節),是因為 Redis 存放的是跨服務共用的基礎設施層狀態,不是任一服務專屬的業務資料——業務資料仍然全部只進 Postgres,Redis 遺失內容不影響任何資料正確性(見第 4 節逐服務降級規則)。

節點分工:

| 節點 | 內容 | 定位 |
|---|---|---|
| VM-1(1 OCPU / 6GB) | 七個服務的複本 A | 無狀態服務節點 |
| VM-2(1 OCPU / 6GB) | 七個服務的複本 B | 無狀態服務節點 |
| VM-3(2 OCPU / 12GB) | Postgres(單例)、Redis(單例)、事件偵測 worker(單例)、TURN server(單例) | 單例元件層 |

分界線是「**這個東西能不能被 Load Balancer 分流**」:能分流的(七個服務的複本)放 VM-1/VM-2,不能分流的(四個單例)全部放 VM-3。理由:

1. **LB 的容錯效果不能被同機的單例抵銷**(核心理由):先前兩節點方案把 Postgres/Redis 固定在 VM-1,若 VM-1 當機,損失的不只是 API 服務複本 A(這部分 LB 本來就能靠複本 B 撐住)——連所有服務都依賴的單例也一併沒了,就算 LB 把全部流量導去複本 B,複本 B 一樣連不到資料庫,等同全站服務中斷。也就是說,「兩節點 + LB」對單一節點故障的容錯承諾,只要故障的剛好是放單例的那個節點就直接破功。把單例全部移出去,VM-1、VM-2 才真正對稱:任一台掛掉只損失一半的 API 運算力。
2. **對稱要徹底才有意義**:worker 留在 VM-1、TURN 留在 VM-2 時,兩台節點只是「都跑複本」,實際負載並不對等——VM-1 多扛 CPU 密集的偵測與轉碼、VM-2 多扛頻寬密集的中繼,兩台當機的後果也不一樣(掛 VM-1 停的是事件偵測,掛 VM-2 停的是直播中繼),LB 的分流假設兩個後端等價,這個假設當時並不成立。單例全部移入 VM-3 後,VM-1 與 VM-2 變成規格、內容、故障後果都相同的兩份複本,LB 的分流才名實相符。
3. **單例的故障域收斂成一個**:worker、TURN、Postgres、Redis 四者都沒有高可用設計(見第 5 節),分散在三台等於三台裡任何一台當機都會少掉某個單例功能;集中在 VM-3 之後,單例故障域只剩一台,VM-1/VM-2 的當機不再影響任何單例功能。代價寫在下面。
4. **OCPU 分配對應負載型態**:事件偵測與 ffmpeg 轉碼是目前唯一的 CPU 密集工作,它移到哪裡、2 OCPU 就跟到哪裡,所以配額從 VM-1 改分給 VM-3;七個輕量服務的複本在 1 OCPU 內綽綽有餘,四 OCPU 總額度不變。

**這次移動放棄了什麼**:修訂 1 當初把資料層獨立出來的理由之一是「資源可視性」——資料層的 CPU/記憶體用量不被事件偵測/ffmpeg 干擾判讀。worker 移入 VM-3 後這一點不再成立,Postgres/Redis 與 CPU 密集工作重新同機,監控上要能分辨「Postgres 慢」與「worker 在轉碼」兩種情況(以容器為單位收集資源指標,不要只看主機層級的平均值)。接受這個代價的理由是上面第 2、3 點:換來 VM-1/VM-2 的完全對稱與單例故障域收斂。相對地也換回一項好處:worker 與 Postgres 同機,事件寫入不再是跨機連線(見第 4 節)。

Load Balancer 只分流七個服務的 HTTP 流量;鏡頭裝置的 RTSP 串流直連 VM-3 的事件偵測 worker,App/Web 的 WebRTC media relay 直連 VM-3 的 TURN server;VM-1、VM-2 上的服務複本存取 VM-3 的 Postgres 與 Redis,一律走 VM 間的 VCN 私有網路——以上路徑都不經過 Load Balancer。兩台服務節點存取資料層都是跨機連線(且兩台一致,不再有「複本 A 同機、複本 B 跨機」的不對稱),這個取捨在第 4 節說明。

## 2. 為什麼現在做微服務拆分

單體服務在一台 VM 上,以此專案的實際流量(單一使用者、幾支鏡頭)撐到幾千個使用者都不是瓶頸——這件事在資料模型與成本分析階段就已確認,拆分本身不解決任何現有的效能問題。

決定拆分的理由是:

1. **免費層允許不花錢做這件事**:Ampere A1 額度是一個資源池(4 OCPU / 24GB),可以自由決定切成一台或多台,不拆成多台不會拿到更多資源,拆成兩台也不會少拿資源——分兩台是免費的。
2. **兩台之後,Load Balancer 才有實質意義**(見第 3 節),否則掛一個 LB 在單一節點前面只是裝飾,騙不了懂架構的面試官。
3. **服務邊界現在切,以後真的要橫向擴展時遷移成本低**——先把邊界定清楚,之後某個服務真的吃緊,只是把它從「兩台各一份複本」改成「更多份複本」,不需要重新設計。

## 3. Load Balancer:為什麼單一節點時不該做、兩節點後該做

單一節點前面放 LB,後面永遠只有一個目標,那不是負載均衡,只是多一跳網路延遲——這是本專案原本(單 VM)方案下的判斷,維持不變。

兩台 VM 都跑七個服務的複本後,LB 前面有兩個真實目標。但這兩個目標帶來的兩個效果,
**現階段只有一個是真的**:

- **容錯(真正的理由)**:任一節點重啟或當機時,另一節點仍可回應七個服務的請求,
  使用者對單節點故障基本無感。這是掛 LB 的唯一實質理由。
- **分流(現在還不是需求)**:兩節點各自只需處理約一半的 HTTP 請求量——但以本專案的
  實際流量(單一使用者、幾支鏡頭的 JSON API),單機撐到幾千個使用者都不是瓶頸
  (第 2 節)。這是預留的餘裕,不是現在要解決的問題,不應該拿它當作掛 LB 的理由。

**要特別誠實的一點:真正會吃滿資源的流量根本不經過 LB。** 依 `00_PRD_需求書.md`
第 9 節的瓶頸排序,前兩名是 TURN 中繼流量與 VM-3 的 CPU(事件偵測 + ffmpeg),
兩者都不在 LB 後面——LB 擋在唯一不吃力的那條路徑前面。這不代表 LB 沒有價值
(節點容錯仍然只有它能提供),但它**不是**影音或運算負載的擴展手段;那兩者各自的
擴展路徑寫在 PRD 第 9 節,都不是 Load Balancer。

Load Balancer 不涵蓋 Postgres、事件偵測 worker、TURN server——這三者都是單例,
沒有第二個目標可以分流,見第 5 節說明為什麼現階段不做這三者的高可用。

## 4. CAP:不套用抽象的三選二,改成逐服務寫下 C/A 選擇

本專案只有一個 Postgres 節點,沒有資料分區(partition)的情境可言,套用 CAP 定理討論資料一致性是在討論一個不存在的拓撲。拆成三台 VM 後(VM-1/VM-2 跑無狀態服務複本、VM-3 跑四個單例),**任一服務複本存取資料層都是跨機連線**,VM-1、VM-2 兩邊都可能遇到「連不到 VM-3」的情境——這是明確的取捨:換來無狀態層與單例層的職責分離(第 1.1 節),代價是兩台服務節點都暴露在同一種網路分區風險下。好處是這個風險現在**對稱**:兩台的行為與降級路徑完全一致,不像先前複本 A 與 Postgres 同機、對這種分區天生免疫,只有複本 B 會踩到。逐服務判斷如下:

| 服務 | 服務複本連不到 VM-3(Postgres/Redis)時 | 選擇 |
|---|---|---|
| Auth | 拒絕登入/註冊請求,回傳 SRV_002,不允許憑舊快取資料驗證密碼 | 一致性(C)——帳密驗證錯了會造成安全問題,寧可暫時無法登入 |
| Device | 拒絕配對/重新命名/移除等寫入操作;裝置列表若有快取可降級顯示 | 寫入選 C,唯讀列表可選 A(顯示「資料可能非最新」) |
| Stream 訊令 | 拒絕建立新的直播 session(需要查詢裝置狀態與寫入 session 記錄) | 一致性(C)——連線失敗比連到錯誤的裝置狀態安全 |
| Event | 時間軸查詢失敗時,回傳錯誤而非空列表(避免使用者誤以為沒有事件);背景 worker 與 Postgres 同機(VM-3),寫入不經過網路,不受此處的跨機分區影響——worker 只在 Postgres 本身不可用時才本機重試 | 讀選 C(寧可顯示錯誤,不可顯示假的空結果),worker 寫入選 A(重試) |
| Push | 若當下無法查出使用者的 push token 清單,延後重試,不立即失敗 | 可用性(A)——推播晚到比整個請求失敗合理 |
| Media | 拒絕新的剪輯/截圖請求(需要寫入 media_items) | 一致性(C)——避免產生無法追蹤來源的孤兒檔案 |
| Album | 唯讀列表可用快取降級顯示;刪除/匯出等寫入操作拒絕 | 讀選 A,寫選 C |

**規則**:任何會寫入 Postgres 的操作一律選 C(寧可失敗,不可資料不一致);純讀取且已有本地/CDN 快取可退的情境選 A。這比套用抽象的 CAP 三選二更有實際指導意義。

Redis 是單例,連不到時依用途分別降級,不套用同一套規則:

| 用途 | Redis 連不到時 | 選擇 |
|---|---|---|
| Stream 訊令 session 暫存 | 拒絕建立新 session,回傳 `SRV_002` | 一致性(C)——連線失敗比連到一半遺失狀態的殘破連線安全 |
| Push 防洗版計數窗 | 計數窗視為未開始,事件直接觸發推播 | 可用性(A)——寧可短暫多推播,不可漏推 |
| 全站請求限流 | 直接放行請求(fail-open) | 可用性(A)——限流是保護機制,故障時不應讓限流本身變成阻斷全站的原因 |

## 5. 刻意不做的事:database-per-service、Postgres 複寫、CQRS、自架入口

**database-per-service**:微服務教科書常見做法,但成本是每個服務要自己處理跨服務的資料一致性(通常靠 event sourcing 或 saga pattern),複雜度遠高於現在的 Postgres 單例 + schema 共用。現階段查詢都是單表或簡單 join(裝置列表、事件時間軸分頁),沒有這個必要。**觸發點**:當某個服務的業務資料本身(如 `push_tokens`)存取模式跟其他服務差異大到需要換一種資料庫技術時,才個別評估把該服務的資料表整個搬遷,不是整批搬。注意這與第 1.1 節新增的共用 Redis 是兩回事:Redis 存放的是不進 Postgres 的短效共享狀態(session/計數/限流),`push_tokens` 等業務資料表目前仍完整留在 Postgres,並未觸發此處的搬遷判斷。

**Postgres 複寫/高可用**:免費層資源有限,做 Postgres 主從複寫会再吃掉一部分 CPU/記憶體,且複寫本身的維運複雜度(failover、資料落後)不是這個規模該優先解決的問題。現況:Postgres 單點故障 = 全站唯讀操作降級、寫入操作全部失敗,這是刻意接受的風險。**觸發點**:當單一 Postgres 的查詢延遲或連線數開始成為瓶頸時,先加 read replica(只解決讀取擴展),不是直接跳去多主複寫。

**CQRS**:讀寫模型分離的成本是兩邊靠事件同步、讀到的資料可能延遲——現在的查詢形狀單純(裝置列表、事件分頁、相簿分頁),沒有複雜到需要獨立的讀取模型。**觸發點**:當某個畫面需要跨服務聚合資料(例如首頁同時顯示裝置狀態+最新事件+推播未讀數,現況分三次呼叫由前端組合),且這種聚合查詢的效能開始拖累原本的寫入路徑時,才評估為該畫面建立一個獨立的讀取模型(不必整個系統套 CQRS,只針對那個查詢)。

**自架 Nginx 當入口取代 Oracle Load Balancer**:Nginx 的 `upstream` 有 round-robin/least_conn、`max_fails` 被動健康檢查與失敗重送,後端分流完全做得到,這不是爭點。爭點是**入口自己掛掉誰接手**:Nginx 必須跑在某台 VM 上,而唯一合理的落點是 VM-3(放 VM-1 或 VM-2 會新增一個故障域;VM-3 因為 Postgres 單例本來就是全站硬單點,擺在那裡不會讓可用性更差)。真正的否決理由是**資源**:VM-3 的 2 OCPU 是全系統瓶頸(第 6 節),事件偵測與 ffmpeg 已經在搶,再把 TLS handshake 與反向代理搬回同一台不划算;而 Oracle Flexible LB 是託管服務,不佔用 4 OCPU / 24GB 的 Ampere 額度,免費層本來就給一個,不用也不會把額度還給 VM。免費版 10 Mbps 的頻寬上限在這個架構下不構成限制——RTSP 直連 VM-3、WebRTC media relay 直連 TURN、影片走 R2 presigned URL,都不經過 LB,LB 只扛 JSON API 與 signaling。**觸發點**:若之後要消除 VM-3 這個單點(例如 Postgres 加 failover),或需要路徑路由/限流等 LB 做不到的能力,再重新評估——屆時的正解多半是「Oracle LB 在外層做節點容錯,Nginx 各跑一份在 VM-1/VM-2 內部當反向代理」,而不是拿 Nginx 取代 LB。

**由 VM 供應 Web 前端靜態檔**:Web 端是瀏覽器端渲染的前端(見 `00_PRD_需求書.md` 第 5 節),不需要伺服器端渲染,所以不引入 Apache 這類 web server——它的強項(mod_php 等伺服器端渲染)在這裡完全用不到,引入只是多一套技術棧。靜態檔改由 Cloudflare Pages 託管:零 VM 資源、免費層靜態流量不限量、TLS 與邊緣快取內建,而且靜態檔流量不會佔用 LB 的 10 Mbps。用 R2 開公開 bucket 當網站主機技術上可行,但 Pages 才有建置流程、SPA 路由 fallback 與部署版本回溯。

**Redis 作為通用快取層**:第 1.1 節的 Redis 用途刻意限定在三項短效狀態(Stream session、Push 計數窗、全站限流),不擴大成「幫 Postgres 查詢做快取」的通用快取層。理由是現階段查詢量小,Postgres 索引查詢(如裝置列表、事件分頁)延遲不是瓶頸,加一層快取只會多一個「快取與資料庫不一致」的風險來源,沒有對應的效能收益。**觸發點**:當某個高頻讀取的 Postgres 查詢(如裝置列表)在實測中出現明顯延遲、且已確認是查詢本身而非網路或前端問題時,才評估把該查詢結果放進 Redis 做短 TTL 快取,一次只擴大一個查詢的範圍,不整批套用。

## 6. 容量結論

VM-3 分到 2 OCPU / 12GB,因為事件偵測與 ffmpeg 剪輯轉檔移到了這裡,那是目前唯一的 CPU 密集工作、且是單例不可分攤;2 OCPU 的配額跟著這個工作走,而不是跟著某台機器。同機的另外三個單例都不是 CPU 消耗者:TURN 中繼是頻寬密集,Postgres/Redis 在目前查詢量(單表/簡單 join、少量短效 key)下遠低於 1 OCPU——所以四個單例共用 2 OCPU 的實際競爭者只有 worker 一個。VM-1、VM-2 各 1 OCPU / 6GB 跑七個輕量服務的複本,綽綽有餘。全部元件加總的尖峰記憶體約 1~2.5GB,分散在三台合計 6+6+12=24GB 的額度裡完全不是問題。

真正的限制跟原本單機時一樣是那 2 個核心——現在是 VM-3 的,而不是單體方案的 4 個。如果事件偵測+剪輯轉檔的並發量有感變慢,是預期中的取捨,不是 bug。新增的觀測要求見第 1.1 節「這次移動放棄了什麼」:worker 與資料層同機,主機層級的 CPU 平均值不再足以判讀,要以容器為單位看。

## 7. 何時該重新評估這份 ADR

- 需要真正的水平擴展(不只是兩份複本,而是依負載動態增減節點數)時,评估改用 Oracle 的 Instance Pool + Autoscaling,但這會超出 Always Free 額度。
- 事件偵測/剪輯轉檔的 CPU 需求持續超過 VM-3 的 2 OCPU 時,先評估在現有 4 OCPU/24GB 池內重新分配(例如從 VM-1 或 VM-2 挪出部分 OCPU 給 VM-3,前提是服務複本的實測負載仍有餘裕),而不是直接開第四台 VM 或加付費資源。若瓶頸確認來自 worker 與資料層互相干擾(而非總量不足),則把 worker 單獨移回一台專用節點,這等於部分回退本次修訂,決策依據是屆時的實測而非預設。
- 任何一個服務的讀寫模式跟其他服務顯著不同,導致共用 Postgres 出現效能衝突時,重新評估第 5 節的 database-per-service 判斷。

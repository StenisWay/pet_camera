## 1. 使用者故事

作為飼主,我希望寵物在鏡頭前有動作時系統自動錄下片段。

## 2. 功能說明

### 2.1 觸發邏輯

偵測服務對每個影格計算 confidence score,超過門檻值(預設 0.6)時觸發事件。錄影期間內偵測到的後續活動視為同一事件延續,不建立新事件。

### 2.2 錄影長度

觸發後開始錄影;活動停止(confidence score 持續低於門檻)超過 5 秒後結束錄影;單一事件最長錄影上限 60 秒。

### 2.3 後處理流程

1. 錄影結束,事件寫入 `events` 表,`status = processing`。
2. 產生影片檔與縮圖。
3. 依 R2 key 命名規則上傳影片與縮圖。
4. 上傳成功,`status = ready`,`confidence_score` 取事件期間最高值。
5. 上傳失敗,`status = failed`。
6. `status = ready` 後呼叫 Push 服務的內部端點 `POST /internal/notifications/event-ready`
   (見 `09_spec_推播通知.md` 第 3 節)觸發推播,Push 回 `202` 後於背景發送,worker 不等待
   發送結果。Event 只送出 `event_id`、`device_id`、`confidence_score`、`thumbnail_object_key`、
   `started_at`(body 格式以 `09_spec_推播通知.md` 第 3 節為準);通知標題需要的裝置名稱由
   Push 服務自行向 Device 服務解析——`devices` 表屬於 Device 服務,Event 不該為了組一則通知
   去讀別人的表(見 `13_ADR_微服務與三節點部署.md` 第 1 節)。

錄影因鏡頭斷線而提前結束時,已錄製的部分仍照上述流程上傳並收斂為 `ready`,同時把
`events.is_partial` 設為 `true`(見 `01_資料模型與儲存規格.md` 第 2.3 節),時間軸據此顯示
`EVENT_003`「此片段不完整」。這不能用 `failed` 表達:`failed` 的語意是「沒有可播放內容」,
而斷線產生的片段是「可以播放,只是不完整」,兩者對使用者的意義完全不同。

## 3. 邊界案例

| 情境 | 預期行為 |
|---|---|
| 短時間內連續觸發 | 依 2.1 合併為同一事件 |
| 錄影中鏡頭斷線 | 已錄製部分仍嘗試上傳並建立事件,`duration_sec` 反映實際長度,`is_partial = true` |
| 上傳 R2 失敗 | 重試 3 次,指數退避;全部失敗則 `status = failed`,不建立可播放內容 |
| 單一事件錄影超過 60 秒上限 | 強制結束錄影 |

## 4. 讀取狀態(反映於時間軸)

| 事件狀態 | 時間軸卡片呈現 |
|---|---|
| `processing` | 縮圖佔位 + 卡片內小型 spinner + 「處理中」文字,不可點擊播放 |
| `ready` | 正常縮圖 + 可點擊播放 |
| `failed` | 卡片顯示 EVENT_001 錯誤圖示,不可點擊播放 |

## 5. 錯誤碼

| 錯誤碼 | HTTP Status | 說明 | 使用者訊息 | 呈現方式 |
|---|---|---|---|---|
| EVENT_001 | 409 | 影片上傳失敗(重試 3 次後仍失敗);`status = failed` 的事件請求播放時亦回此碼 | 此片段處理失敗 | 時間軸卡片內嵌錯誤圖示 |
| EVENT_002 | 503 | 偵測服務無回應 | (不對使用者顯示,記錄後端日誌) | - |
| EVENT_003 | - | 錄影中斷(鏡頭斷線),即 `status = ready` 且 `is_partial = true` | 此片段不完整 | 時間軸卡片內嵌提示 |

## 6. 驗收標準

- [ ] 寵物活動停止後 5 秒內結束錄影
- [ ] 事件從觸發到 `status = ready` 實測延遲 < 30 秒
- [ ] 連續動作只產生一筆事件
- [ ] 上傳失敗時事件標記 `failed` 並顯示 EVENT_001,不產生孤兒資料
- [ ] 單一事件錄影超過 60 秒強制結束
- [ ] 鏡頭斷線產生的不完整片段標記 `is_partial = true`,仍可播放並顯示 EVENT_003
- [ ] `status = ready` 後確實呼叫 Push 的內部端點,且失敗不影響事件本身已 ready 的狀態
